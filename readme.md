# Custom Thread Pool

## Что реализовано

В проекте реализован собственный пул потоков без использования `ThreadPoolExecutor` как основного механизма исполнения.

Поддержаны следующие возможности:

- `corePoolSize` — базовое количество потоков;
- `maxPoolSize` — максимальное количество потоков;
- `keepAliveTime` и `timeUnit` — время простоя потока до завершения;
- `queueSize` — ограничение на размер очереди;
- `minSpareThreads` — минимальное число свободных потоков, которое пул старается поддерживать;
- несколько очередей задач;
- распределение задач по принципу `Round Robin`;
- fallback на наименее загруженную очередь;
- настраиваемая политика отказа;
- `ThreadFactory` с логированием создания и завершения потоков;
- методы `execute`, `submit`, `shutdown`, `shutdownNow`;
- демонстрационная программа в `Main`.

---

## Архитектура решения

Пул содержит несколько независимых очередей задач — по одной на потенциальный worker.

Каждый worker работает со своей закрепленной очередью. Это упрощает модель:

- worker читает задачи только из своей очереди;
- входящие задачи распределяются по очередям циклически;
- если выбранная очередь переполнена, пул пытается найти менее загруженную очередь;
- если свободных потоков становится меньше `minSpareThreads`, пул может заранее поднять новый worker.

Такой подход позволяет уменьшить конкуренцию за одну общую очередь и дает больше контроля над балансировкой нагрузки.

---

## Принцип работы

### Поступление задачи

При вызове `execute` или `submit` пул работает так:

1. Проверяет, не переведен ли он в состояние `shutdown`.
2. Проверяет, хватает ли свободных потоков относительно `minSpareThreads`.
3. Выбирает очередь по `Round Robin`.
4. Если очередь заполнена, ищет очередь с минимальной загрузкой.
5. Если все очереди заняты, пытается поднять новый worker, если это не превышает `maxPoolSize`.
6. Если задача все равно не может быть принята, применяется политика отказа.

### Работа worker

Worker:

- ожидает задачу из закрепленной очереди через `poll(keepAliveTime, timeUnit)`;
- выполняет задачу и пишет лог;
- при простое дольше `keepAliveTime` завершает работу, если число потоков больше `corePoolSize`;
- при `shutdown()` завершает работу после обработки уже взятых задач и опустошения своей очереди.

## Политика отказа

В демонстрационной версии используется `CallerRunsPolicy`.

### Почему выбрана именно эта политика

Эта политика создает естественный backpressure:

- если пул перегружен, задача выполняется в потоке, который ее отправил;
- источник нагрузки автоматически замедляется;
- система продолжает работать даже в условиях перегрузки.

### Недостатки

У этого подхода есть минусы:

- поток отправителя может блокироваться на выполнении задачи;
- может вырасти latency для вызывающего кода;
- поведение системы становится менее предсказуемым по времени ответа.

### Альтернатива

В коде также предусмотрена `AbortPolicy`, которая сразу отклоняет задачу и выбрасывает `RejectedExecutionException`. Такой вариант полезен, если важнее строго ограничить время ответа и не нагружать поток-отправитель.

---

## Балансировка задач

Основной механизм балансировки — `Round Robin`.

Это значит, что новые задачи распределяются по очередям по кругу:

- первая задача в очередь 0;
- вторая в очередь 1;
- и так далее.

Если выбранная очередь переполнена, включается fallback:

- пул ищет очередь с минимальной текущей загрузкой;
- если такая очередь найдена и в ней есть место, задача помещается туда.

Такой подход сочетает простоту и более равномерное распределение нагрузки.

---

## Логирование

В системе реализовано подробное логирование всех ключевых событий:

- создание потока;
- завершение потока;
- прием задачи в очередь;
- выполнение задачи;
- idle timeout;
- отклонение задачи;
- запуск задачи в caller thread при перегрузке;
- перевод пула в `shutdown`.

По логам можно понять текущее состояние системы и проследить жизненный цикл worker-потоков.

## Анализ производительности

### Сравнение со стандартным `ThreadPoolExecutor`

Стандартный `ThreadPoolExecutor` из JDK будет эффективнее и надежнее, потому что:

- давно оптимизирован;
- хорошо протестирован;
- поддерживает большое количество сценариев и edge-case’ов;
- уже содержит зрелые механизмы управления worker lifecycle и rejection policy.

Моя реализация уступает стандартной библиотеке по зрелости и универсальности, но дает преимущества в учебных и исследовательских целях:

- проще встроить собственную логику балансировки;
- проще контролировать внутренние события;
- можно добавить domain-specific правила масштабирования и распределения задач.

### Сравнение с Tomcat / Jetty

Tomcat и Jetty используют более зрелые модели обработки сетевых запросов, backpressure и управления ресурсами.

Текущая реализация — это в первую очередь учебный кастомный executor, который демонстрирует принципы построения пула и допускает дальнейшее расширение.

## Мини-исследование параметров

### `corePoolSize`

- слишком маленькое значение ухудшает реакцию на всплеск нагрузки;
- слишком большое создает лишние потоки и увеличивает overhead на переключение контекста.

Для CPU-bound задач обычно разумно выбирать значение близкое к числу ядер.
Для I/O-bound задач значение может быть выше.

### `maxPoolSize`

- маленький `maxPoolSize` быстро приводит к отказам под burst-нагрузкой;
- слишком большой — к oversubscription CPU и росту context switch overhead.

### `queueSize`

- маленькая очередь снижает latency, но увеличивает риск отказа;
- большая очередь уменьшает вероятность rejection, но может сильно увеличить tail latency.

### `keepAliveTime`

- маленькое значение быстрее освобождает ресурсы после пиков;
- слишком маленькое может вызывать частое создание и завершение потоков;
- слишком большое оставляет лишние простаивающие потоки.

### `minSpareThreads`

Этот параметр позволяет держать резерв готовых worker’ов.

- низкое значение увеличивает холодный старт при всплеске;
- высокое — расходует ресурсы даже при низкой нагрузке.

### Вывод

Максимальная производительность достигается подбором параметров под характер задач:

- для CPU-bound нагрузки — умеренное число потоков и небольшая очередь;
- для I/O-bound нагрузки — допустимо больше потоков;
- для burst-нагрузки полезны `minSpareThreads` и политика типа `CallerRunsPolicy`.

---

## Демонстрационная программа

В `Main`:

- создается пул с параметрами:
    - `corePoolSize = 2`
    - `maxPoolSize = 4`
    - `queueSize = 2`
    - `keepAliveTime = 5 seconds`
    - `minSpareThreads = 1`
- отправляются `Runnable`-задачи;
- отправляются `Callable`-задачи;
- демонстрируется перегрузка и работа политики `CallerRunsPolicy`;
- вызывается `shutdown()`;
- по логам отслеживается создание потоков, выполнение задач, idle timeout и корректное завершение worker’ов.
